# Minimal production integration plan: native Chromium window

Decision boundary: keep0.16 unchanged. Develop this as a separate experimental backend after the0.16 release. The exact immutable Engine0.1 already runs a sandboxed, ordinary native window with `navigator.webdriver=false`, native prompts, WebGL, video and the existing PCM helper. The remaining work is product/runtime integration, not an unproved browser engine replacement. No CDP or automation/identity override belongs in this backend.

## Smallest implementation architecture

Create a separate `NativeWindowSession extends EventEmitter`, selected by a session factory. Do **not** subclass the current BrowserSession: its constructor, mixins, tab sessions, media watcher, input guards and cookie checkpoint path assume CDP. Keep pure shared modules—URL/input validation, secure storage, VehicleAudioBridge, frame sender and driving/visibility gate—and preserve the existing BrowserClient request/event contract where the behavior is equivalent.

The backend currently creates BrowserSession at server.js:23, forwards its frames/events and dispatches ordinary operations in one switch. A factory changes that construction point; the frontend/client IPC can keep the current512KiB JSON and4MiB frame limits. Add one explicit backend capability snapshot so native browser prompts and native Find are displayed/controlled as native UI, rather than opening the old CDP dialog/auth/permission panels. Refactor the diagnostic `pageInfo().result.value` assumption at the single server callsite; do not invent a fake CDP transport to satisfy it.

Keep native browser prompts as the authority. Native omnibox access also exposes normal Chrome/internal/local schemes beyond the current HTTP(S)-only backend navigation API; make that policy choice explicit. A content script must not grant site permissions, answer credentials or synthesize page events merely to mimic a desktop action. Native capture already shows those normal interfaces. Existing optional vault actions can later be ported as explicit HTTPS/user-requested extension operations; they are not an automatic consequence of the metadata proof.

## Pipe/codec boundary

Use a pull-capture protocol: Node requests a picture only when the existing frameSender.canSend() is true and no prior capture is pending. Native helper converts XImage BGRX to tightly packed RGBA, tags it with run/document epoch, request ID and geometry, and writes on a **separate frame descriptor**. Control/ACK traffic uses separate bounded pipes so blocked pixel delivery cannot stall controller input. Retain exactly one immutable partially-written frame; reject extra capture credits as busy. Finish/drain old-epoch partial frames with their old tag; never overwrite their bytes. Stop/release has a bounded deadline.

The helper must validate version/opcode/body length, coordinates, modifiers, key whitelist, wheel counts and epoch before XTest; process stdin fragmentation/coalescing; release held keys/buttons on epoch change/EOF/stop; detach/delete shared memory. It must not offer shell, arbitrary path, process or file-read operations. The authored helper explicitly scopes text/clipboard as unsupported rather than silently truncating or pretending ASCII covers Unicode. Its ACK confirms queuing to X, not that Chrome has finished processing or painting the action; preserve a separate focus/readiness barrier.

Feed native RGBA into the existing FrameDelta sender and frontend image bridge; no Chromium JPEG/base64/Node JPEG decode is needed for the headunit. Keep generation resets and latest-frame/backpressure semantics. Current frame wire limit is4MiB including its header:1280×400 and1600×533 fit,1600×900 does not. Do not raise limits accidentally. Set performance codec to `rgba-native` rather than incorrectly reporting `jpeg-native`.

Phone preview currently relies on screencastJpeg; native mode therefore needs an explicitly bounded low-rate JPEG encoder when a paired phone is actually polling. This is routine codec work, but CPU/pressure must be measured. Do not continuously encode a second stream while headunit/audio is under pressure.

## Native controller and viewport behavior

Map the existing queued rotary focus/press barrier to native Tab/Shift+Tab plus role-appropriate activation. Preserve cancellation on local navigation, real document/tab changes, native prompt/UI-mode changes, blocked/stop and bridge reconnect. Track native windows (including popups) and use the focused owned window plus active tab; do not treat a temporary native GTK focus as app invisibility. Bind the context to run epoch + active tab + browser-supplied document ID; reject stale queued input before writing it. Parent IFRAME focus is delegating metadata: select the focused child from a verified frame/document tree, not the last global event.

Page focus metadata does not describe Chrome's omnibox, HTTP-auth fields or GTK widgets. Manual native keyboard/touch already works; automatic masked keyboard and complete controller parity for these interfaces still require focused native role metadata (AT-SPI or an equally bounded native UI adapter). Unicode/bulk text needs a private UTF-8 clipboard/selection owner followed by native Ctrl+V, or a qualified native input-method path. Keep short key-driven PIN behavior. Structured date/time fields, password masking, drag/drop and cross-frame focus need actual native regression coverage before claiming0.16 input parity.

The current frontend repeatedly resizes the browser when its toolbar/keyboard/fullscreen changes. Xvfb proof uses a fixed desktop. For native mode choose one physical desktop size matching the web surface and preserve its aspect ratio; frontend fit/letterbox transforms must map input to actual desktop pixels. Treat `resize` as layout negotiation and extension native zoom, not a display-server restart per keyboard toggle. Hide duplicate MGU chrome through an explicit native layout/capability; keep vehicle controls and Menu/Back reachable. Video fullscreen uses the entire desktop and must never be a crop of a taller virtual screen.

GTK header bars keep Open/Cancel/location visible at400px, but directory-list minimum height still extends below the screen. Resolve unrestricted browsing with qualified compact sizing or bounded **dialog-only** focus-follow/repositioning; keep the main browser/video desktop at its true size. This is a concrete UX gap, not a reason to assume all dialogs fit.

## Process/runtime/package shape

Add a separately versioned immutable native-GUI component; leave Engine0.1 untouched. It contains a coherent private2.36 Xvfb/GTK/XTest/WM/D-Bus stack plus required MIME/icon/schema/font/XKB/gconv/locale data and authored helper/extension/host. Node8 and firmware audio helper remain in their existing libc domains. The current245-package/133MiB compressed/~555MiB extracted scratch closure is deliberately overbroad; prune/build an explicit runtime closure before release. Configure absolute prefixes at build time instead of retaining prototype XKB shims or accidental host paths. Retain exact package/source URL/hash manifests and produce full notices/corresponding-source availability; xfwm4 adds GPL obligations. Existing Chromium provenance does not license the new runtime or any proprietary CDM.

Extend the existing root privilege-dropping launcher only for private namespace/config preparation: private X socket directory,0600 random MIT cookie, no X TCP, files/dns-only NSS view, correct private data paths and shared IPC namespace for server/capture. Then run browser/server/WM/bridge/helper as the existing service UID3911. NativeMessaging executable/manifest/extension must be immutable root-owned configuration; the host remains non-setuid. Endpoint0600/parent0700 plus SO_PEERCRED and exact extension-origin allowlist remain mandatory.

One unprivileged native supervisor owns all children and shutdown/reaping; retain PDEATHSIG and the existing systemd KillMode=control-group backstop. NativeSession.stop must stop every native child on normal app hide while the service remains running, not only on service exit. Test Chrome/helper/Xserver/extension failure and parent SIGKILL; drain/discard stale frames, close audio, remove auth/socket/SHM and emit blocked once. Reuse existing profile stop-before-snapshot/restore/storage limits; do not weaken root startup diagnostics or gate freshness.

## What blocks release versus ordinary implementation

**Release blockers:** physical MGU kernel/IPC/X11/sandbox/resource qualification; measured native memory about650–675MiB on host and uncertain headunit headroom; complete controller/native-widget masking/Unicode/chooser behavior; epoch/resync/bounded metadata lifecycle; encrypted profile/partitioned-cookie hard-kill recovery; final minimized signed/provenanced runtime and source/notices obligations. Exact old-base Ubuntu18 success proves userspace compatibility, not vehicle qualification.

**Routine integration with proven interfaces:** separate session factory/facade, frameSender reuse, native key/pointer plumbing, tabs/URL/title/mute/download adapters, existing audio bridge, explicit native UI capabilities, low-rate phone preview encoder and exact-package CI. These still need tests; they do not require CDP, a new engine, webdriver spoofing or provider-account experiments.

Accept the native backend only after the existing frontend/client/protocol/gate/audio/recovery suites pass in both modes and exact-package tests cover the new runtime. Keep the experimental component opt-in until an actual MGU trial confirms startup, native text/controller behavior, continuous video, audio release/reacquisition and memory stability. Do not silently migrate0.16 users or claim protected-provider playback from local fixtures.
